# CHEAT / WORLDLINE TECHNICAL RULE COMPENDIUM — V9 TECHCLOSE3

## Status

**CURRENT-HIGH rule index and taxonomy bridge.**

This file consolidates the cheat-related rules already distributed across the V8/V9 technical canon. It is a routing/control document: where a local engine, airframe, ship, vehicle, weapon, computation, cryptologic or combat ledger gives a more specific state, that local ledger controls the value. The purpose here is to prevent stage skipping, double counting and accidental cloning of Asai's personal foreknowledge.

## 1. Three independent questions must always be separated

Every worldline technical delta must answer three different questions.

1. **Knowledge/cheat distance:** who possesses the answer-selection advantage or transferred method? Use `CD0-CD4`.
2. **Technical transformation state:** what has actually changed in the design, material, subsystem, integrated article or qualification state? Use the domain taxonomy such as `H->C->M->E->P->I->A`, `EH->EC->EMQ->ES->EI->EA`, `EA/PA/CI-D/Q/S`, `EX0-EX3`, `FCS0-FCS4`, `R0-R3`, or `ID0-ID5/IDH`.
3. **Realization/service state:** has the result been required/adopted, physically built or refitted, serially reproduced, allocated, serviceable, forward, used in combat, and demonstrated under the actual environment?

A closure on one axis never closes the other two automatically.

## 2. Core cheat rules

### 2.1 Historical date is an anchor, not a capability ceiling

A later historical invention date is not by itself an engineering veto. Reject or delay a worldline result only by identifying an unpaid physical or institutional gate: material/process, geometry, precision, measurement, test duration, cooling, vibration, endurance, yield, installation, supply, manpower, training or another causal constraint.

### 2.2 Strong idea gate, real physical gate

At explicit `CD0` intervention, Asai may strongly compress answer selection, identify promising architecture, avoid known dead ends and start the correct long-lead tests early. This does not supply unknown measured coefficients, remove manufacturing defects, complete endurance hours, or create industrial yield.

### 2.3 Long clocks may be prepaid only through a causal start event

Creep, oxidation, fatigue, corrosion, bearings, combustion, cooling, process capability, field-return statistics and specialist training can mature early if there was a reason and resource to start them early. Foreknowledge may identify the clock; the elapsed physical/test/organizational time must still be paid.

### 2.4 No second cheat multiplier

A value already rebaselined through Asai foreknowledge, computation, test/QC and industry must not receive another generic `reincarnator bonus`. Any further delta needs a named previously unpaid capability, corrected accounting item or newly closed local gate.

### 2.5 No generic computation/performance scalar

`Asai computation exists -> +X% speed / output / accuracy / ship performance` is forbidden. Credit computation through a named channel: design-space search, test reduction, error separation, weight/trim cases, vibration, thermal/flow comparison, calibration, table generation, scheduling, QC or faster redesign.

### 2.6 Calculation time is not physical time

Arithmetic and comparison may accelerate sharply. Machining, endurance running, curing, corrosion exposure, flight/sea trials, teardown, field training and serial learning remain physical clocks unless a separate parallelization/capacity change is paid.

### 2.7 Capability is not procurement or combat power

The default no-backflow chain is:

`capability -> local integration -> physical article/refit -> qualification -> requirement/adoption -> serial production/refit release -> allocation/fit -> serviceable -> forward -> combat use -> observed effect`

This is a **gate checklist, not a universal calendar order**. Private/company prototypes may precede a military requirement, and a requirement may precede a prototype. But a service/combat claim must close every relevant intervening gate.

### 2.8 Difference-led history

Use `historical/previous state -> causal delta -> new state`. Do not rebuild the world from zero at each gate and do not erase unaffected historical structures. Conversely, do not copy historical performance, readiness or loss merely because the designation remains familiar.

### 2.9 Later outcome does not back-propagate

A later successful first flight, qualification, field validation, production release, combat lesson or organizational state does not exist at an earlier checkpoint unless an earlier file explicitly closes it. Future technical snapshots and branch-neutral envelopes are not past physical inventory.

### 2.10 Enemy and other organizations do not receive zero-lag copies

External diffusion requires an actual channel: observation/intelligence/capture/publication, recognition, requirement change, development, production and fielding. The same applies inside Japan when a method has not yet been transferred.

## 3. Cheat distance / knowledge ownership — `CD0-CD4`

- **CD0 Asai personal:** explicit personal design/review. Strong search-order/known-failure advantage; physical gates remain.
- **CD1 Asai core organization:** institutionalized standards, test infrastructure, failure taxonomy, calculation forms, QC and accumulated architectures. Staff are not reincarnators.
- **CD2 supported customer / secure room:** purchased machines, generic forms, training, maintenance, interfaces and contractually transferred methods. Customer-secret inputs may remain local.
- **CD3 autonomous institution:** bureau, arsenal, shipyard, manufacturer or service technical office has absorbed the workflow and solves domain problems with its own experts.
- **CD4 field/operational user:** ship, unit, station or maintenance organization operates issued hardware/doctrine/tables. Design-room foreknowledge does not appear at the field edge.

### Ownership/non-decay rule

Transferred machines, calculation rooms, accepted methods, training, maintenance practice, card/data formats, licensed modules and locally developed improvements remain with the customer. Narrative distance does not confiscate industrial capital.

### No remote reincarnator cloning

Asai's untransferred private answer is not copied into every naval architect, gunnery officer, cryptanalyst, engine designer or field unit. For specialist domains outside Asai's direct expertise, even `CD0` normally supplies architecture/instrumentation/workflow insight rather than a magically correct target-specific solution.

## 4. Customer computation maturity is separate from cheat distance

The retained `U` scale describes how deeply a customer organization uses computation; it is not the same as `CD`.

- **U1:** primarily test/data reduction.
- **U2:** customer proprietary data can be processed locally/securely.
- **U3:** customer-developed calculation forms materially participate in design/technical decisions.
- **U4:** `coarse search -> priority physical test -> recalculation -> independent check` is an organizational standard.

A U4 organization can be `CD2` when using vendor-supported infrastructure or `CD3` when the problem is solved autonomously.

## 5. Aircraft rebaseline pipeline — `H -> C -> M -> E -> P -> I -> A`

This is the current consolidated aircraft transformation method. Numerical examples in older archived parents remain subordinate to later V8/V9 local canon.

- **H — Historical/local baseline:** fix subtype, date, mission weight, engine/supercharger, propeller, fuel, armament, carrier constraints and performance altitude. H is a comparison anchor, not automatically the worldline article.
- **C — Computation/test-analysis delta:** candidate search, flutter/vibration zones, cooling/prop/engine matching, wind-tunnel/flight-test data reduction and redesign calculation. No direct blanket speed/weight bonus.
- **M — Materials/manufacturing/QC delta:** only materials/processes actually certified and producible at that date. Do not re-add a material already contained in H.
- **E — Engine/propulsion installation delta:** take an engine at its valid engine-side state, then close mount, cowl, intake, exhaust, aircraft-side cooling/oil arrangement, accessories, CG and installation losses.
- **P — Propeller delta:** compare from the actual historical/current propeller baseline. Do not roll a mature constant-speed propeller backward to fixed pitch to manufacture a bonus.
- **I — Integrated physical shadow/article:** solve the coupled aircraft: mass/CG, shaft power, exhaust thrust, drag, propulsive efficiency, speed/altitude, climb, range/endurance, turn/stall, dive/flutter/control and carrier handling where applicable. Never sum the maximum independent deltas.
- **A — Adopted/reinvested configuration:** the military/manufacturer decides how to spend technical margin among speed, range, protection, firepower, structure, reliability/life, maintenance, radio/navigation/oxygen and growth margin. Technically possible equipment is not automatically fitted.

After multiple `A` states exist:

- **N — niche regeneration:** compare contemporary adopted states and identify remaining operational gaps.
- **O — original/new program:** regenerate an original requirement/design from the remaining niche rather than preserving an old fictional aircraft simply because it existed in an earlier draft.

`N/O` are comparative downstream steps, not maturity grades of one aircraft.

## 6. Engine-side pipeline — `EH -> EC -> EMQ -> ES -> EI -> EA`

- **EH:** historical engine design/prototype/performance/endurance/failure/production/customer baseline.
- **EC:** engine computation and data work: test reduction, torsion, heat/flow, supercharger/reduction comparison, failure classification and calculation assets.
- **EMQ:** materials, manufacturing and quality: heat treatment, surface treatment, tolerances, gauges, balancing, statistical QC and metrology. EC does not automatically grant EMQ.
- **ES:** engine internal systems: supercharger, reduction gear, fuel metering/injection, ignition, lubrication, internal cooling and accessory drive.
- **EI:** integrated engine state: ratings, altitude map, mass/envelope, BSFC, temperatures/margins, endurance/failure distribution, reduction ratio/prop load and maintenance interval are resolved together.
- **EA:** adoptable engine state: the relevant manufacturer/service can contract, produce, train, procure materials and pass required tests.

Aircraft `E` receives an engine from the engine-side `EA(year,variant)`/availability state; it does not redo the same upstream engine credit.

## 7. Engine/propeller/cooling availability states

### Engine
- **EA-D:** development-flight engine available under manufacturer support/restrictive inspection; not squadron-ready.
- **EA-Q:** service-qualified engine with approved operating envelope and installation qualification.
- **EA-S:** series-repeatable qualified engine; production lots reproduce the state with controlled variance.

### Propeller
- **PA-D:** development aircraft can fly the specified hub/blade/governor/reduction combination under a defined limited envelope.
- **PA-Q:** specified engine-prop-airframe combination has passed representative vibration, overspeed, pitch/governor and flight/control qualification.
- **PA-S:** tooling, gauges and acceptance are frozen enough for repeatable serial manufacture; does not imply unlimited quantity.

### Cooling/oil installation
- **CI-D:** instrumented ground/limited-flight installation under development.
- **CI-Q:** representative hot-day climb, sustained power, high-speed, ground/taxi and altitude oil cases are qualified.
- **CI-S:** baffling/duct/seal/oil-cooler geometry and acceptance checks are serial-reproducible.

`EA`, `PA` and `CI` must be stated separately for high-power aircraft chronology.

## 8. Same name does not mean same hardware — `ID0-ID5/IDH`

These are **change-type tags, not a linear maturity ladder**, and multiple tags may apply.

- **ID0:** near-historical hardware; historical headline spec usable unless locally changed.
- **ID1:** same designation, installed-system delta.
- **ID2:** same designation, production/material/process/QC delta.
- **ID3:** same designation, service-state/readiness/support delta.
- **ID4:** lot/variant/overhaul split; date/serial/lot is mandatory.
- **ID5:** designation remap/collision; ordinary historical same-name data are unsafe.
- **IDH:** historical anchor only; comparison/calibration object, not automatically the worldline production article.

For aircraft, resolve ID state before copying a historical datasheet, then apply the aircraft transformation and service/allocation gates.

## 9. Exhaust state differential — `EX0-EX3`

- **EX0:** collector/common exhaust; no meaningful rearward momentum recovery credit.
- **EX1:** individual exhaust exists but thrust-recovery integration is not the governing objective.
- **EX2:** intentional thrust individual/ejector exhaust; most collector-to-stack gain is already consumed.
- **EX3:** EX2 plus nozzle/back-pressure/direction, cowling/cooling interaction, thermal/support life, repeatability and A/B closure.

Historical EX2 performance cannot receive the full EX0->EX2 card again. Only the residual state differential and separately proven package effects may be credited.

## 10. Materials rule

A material/process improvement must be tied to its actual structural member/process and date. If H already contains the advanced historical material, it is not an extra Asai card. Research maturity, coupon/panel success, full-scale component, flight article, qualification and fleet adoption are separate states.

CFRP, Material No.2/3 and special dense materials therefore retain their own local state ledgers rather than receiving a global future-material bonus.

## 11. Ships and fire control

### Ship headline chain

Do not collapse:

`hull/architecture -> installed machinery -> delivered/serviceable shaft power -> speed at actual displacement/sea state -> WOD -> aircraft operating envelope -> elevator/hangar/deck handling -> embarked -> serviceable -> deck-ready -> sortie cycle`

A gain in one link does not automatically move all later links.

### Fire-control maturity — `FCS0-FCS4`

- **FCS0:** historical/basic chain.
- **FCS1:** historical architecture with improved calibration/QC/boresight/lot control/maintenance.
- **FCS2:** dedicated sight/calculator/workflow/transmission improvement is adopted.
- **FCS3:** integrated gyro/electrical/analog assistance such as synchro/resolver/servo/dedicated continuous analog elements.
- **FCS4:** mature integrated director/automatic-follow-up; requires local system audit.

### Ship integration depth — `R0-R3`

- **R0:** calibration/function package with little structural/electrical alteration.
- **R1:** transmitters/wiring/synchronization/repeaters/power/interface work.
- **R2:** director/AA FCS/switchboard and associated target-allocation integration.
- **R3:** new-build/major-refit architecture with foundations, routing, power, spaces and system integration designed in.

`FCS` and `R` are independent. `FCS3` capability does not mean every ship has it; `R3` infrastructure does not mean future equipment is already installed.

## 12. Central computer versus embedded equipment

A large central calculation machine existing ashore does not imply the same machine can be installed aboard an aircraft, ship or vehicle. Fielded calculation requires a dedicated mechanical/electromechanical/electrical/analog package with its own weight, volume, power, environment, reliability, production, training and adoption gates.

## 13. Cryptography / SIGINT

Machine capability is only part of operational cryptologic power. For a named target/date close:

`collection -> traffic analysis -> target-specific cryptanalytic insight/key/crib/material -> machine processing -> recovery/decrypt throughput -> translation -> intelligence fusion -> dissemination -> operational exploitation`

A CD3 Navy cryptanalytic organization may own strong machines and workflows without receiving Asai's personal answer or automatically breaking a specific enemy cipher.

## 14. OOB / service-state rule

For a historical inventory count, separate:

`historical count -> worldline lot/config mix -> serviceable -> forward -> combat used`

Technical availability never creates a named-unit retrofit quantity by itself. Saved equipment/manpower likewise does not become a different theater's bonus until an allocation event occurs.

## 15. Combat-effect chain

Same hardware name does not fix hit rate, bombing concentration, AA effectiveness, mobility or damage-control outcome. Resolve the local causal chain. For fire effect:

`observation -> sight/sensor -> input/estimate -> calculation/correction -> indication -> boresight/stabilization -> mount/release -> ammunition/ballistics -> crew -> environment -> effect`

For mobility, logistics, damage control and cryptologic exploitation use the equivalent domain chain. Never multiply several upstream improvements onto one historical outcome if that outcome already embeds them.

## 16. Mandatory record for a future technical closure

A new technical closure should record, where applicable:

- date/checkpoint;
- subject/type/variant/lot;
- `CD` distance and concrete transfer channel;
- historical/local baseline and identity tags;
- technical transformation state (`H/C/M/E/P/I/A`, engine/GT/material/FCS/etc. local state);
- physical article/test/qualification state;
- requirement/adoption authority;
- production/refit state and quantity;
- allocation/fit/serviceable/forward state;
- combat/effect state;
- which historical benefit is already consumed, to prevent double count;
- explicit STOP LINE for what remains unclosed.
